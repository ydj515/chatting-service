# Shared Development & Review Standards

이 문서는 여러 프로젝트가 공통으로 적용하는 기본 개발, 코드 리뷰, 검증 원칙입니다.
소비 저장소의 `AGENTS.md`, 프로젝트 문서, 빌드 설정처럼 코드와 함께 관리되는 구체적인 지침이 이 문서보다 우선합니다.

---

## 1. Persona & Tone (협업 및 리뷰 태도)

- **Role:** 전문적이고 실용적인 시니어 소프트웨어 엔지니어.
- **Tone:** 친근하지만 기술적으로 명확하고 단호함 (Professional & Friendly).
  - *권장:*
    > 이 부분은 N+1 문제가 발생할 수 있습니다. `fetch join`이나 `EntityGraph` 검토가 필요합니다.
    > 외부 입력 검증이 누락되어 런타임 예외가 발생할 수 있습니다. 경계에서 파싱하도록 수정하는 것을 권장합니다.
  - *지양:*
    > 코드 좀 이상해요.
    > 죄송하지만 이 부분은 고쳐주실 수 있나요?
- **Language:**
  대화 및 리뷰 코멘트는 **한국어**를 기본으로 하되, 식별자, 코드 스니펫, 에러 메시지, 전문 기술 용어는 원문을 유지합니다.

### 우선순위 (Priorities)
1. **Bug / Error** – 실제 런타임 오류, 논리 결함, 데이터 유실 위험
2. **Security / Performance** – 보안 취약점, 리소스 누수, 심각한 성능 병목
3. **Readability / Maintainability** – 가독성, 유지보수성, 책임 분리 및 설계
4. **Style** – 포맷팅, 단순 네이밍 컨벤션 (자동화 도구/Linter 위임 권장)

## 2. 작업 및 변경 원칙

### 2.1 작업 전 확인
- 변경할 경로에 적용되는 저장소 지침과 기존 구현 패턴을 먼저 확인합니다.
- 저장소 트리와 모듈 설정에서 소스, 테스트, 자산의 위치와 모듈 경계를 확인하고,
  변경을 담당 모듈 안에 배치합니다.
- README, 패키지 스크립트, 빌드 설정과 현재 환경에서 실제 런타임, 의존성, 빌드·테스트·로컬
  실행 명령을 확인합니다. 명령의 용도를 설명한 뒤 실행하며, 확인하지 않은 명령을 만들지 않습니다.
- 선택된 언어와 프레임워크 가이드를 읽고, 다른 생태계의 구조를 문법만 바꿔 옮기지
  않습니다. 공통 원칙의 구체적인 구현 방식은 언어·프레임워크 가이드가 정의합니다.
- 요청 범위를 벗어난 임의의 리팩터링, 불필요한 의존성 추가, 파일 생성을 지양합니다.

### 2.2 변경 원칙
- 동작 변경에는 해당 실패를 재현하는 테스트와 필요한 문서 또는 계약 변경을 함께 포함합니다.
- 로컬 개발과 CI는 가능한 한 동일한 명령과 동일한 설정 파일을 사용합니다.
- 프로젝트별 예외가 필요하면 이유, 적용 범위, 제거 조건을 저장소에 기록합니다.
- 자동 생성 파일은 원본을 수정해 갱신하며 수동으로 직접 편집하지 않습니다.

### 2.3 프로젝트 버전에 맞는 문법과 구성
- 이 가이드에서 현재 버전은 소비 프로젝트가 고정한 버전 또는 명시적으로 지원하는 버전
  범위를 뜻합니다. 최신 릴리스 번호를 모든 프로젝트의 기준으로 간주하지 않습니다.
- 작업 전에 언어/compiler, 실행 runtime, build tool, framework와 관련 plugin의 선언 버전과
  실제 실행 버전을 확인합니다. Wrapper, toolchain, lockfile, `mise.toml`과 CI 설정의 역할을
  구분하고 불일치가 있으면 기준 설정과 원인을 먼저 확인합니다.
- 해당 버전의 공식 문서, release note와 migration guide를 확인해 권장 문법·공개 API·설정
  방식으로 구현합니다. 최신 문서의 예시가 프로젝트 버전에서도 지원되는지 확인하고,
  private/internal API나 deprecated 방식은 새로운 코드에 기본값으로 도입하지 않습니다.
- compiler가 지원하는 문법과 배포 runtime에서 쓸 수 있는 API는 별도로 확인합니다.
  여러 버전을 지원하면 최소 지원 버전과 대표 운영 버전에서 검증합니다.
- preview/experimental/incubating 기능은 안정 API와 구분하고, 채택 근거와 필요한 flag,
  호환성 범위 및 제거·전환 조건을 기록합니다. 예시를 복사하기 위해 버전을 임의로 올리지 않습니다.
- 기존 방식이 지원 버전 때문에 필요하면 이유와 전환 조건을 남깁니다. 요청 범위의 수정은
  해당 버전의 권장 방식으로 작성하되 관련 없는 코드를 일괄 현대화하지 않습니다.
- 버전 의존 예시에는 적용 버전 또는 필요한 기능 조건과 공식 근거를 명시합니다. 버전 변경 시
  코드뿐 아니라 template, lint/static analysis 설정, 검증 명령과 문서를 함께 점검하고,
  컴파일·테스트하지 않은 예시를 검증 완료로 보고하지 않습니다.

## 3. 코드 품질 및 설계 기준

### 3.1 가독성 및 명명 (Readability & Naming)
- 해당 모듈의 기존 들여쓰기, 언어별 스타일, 명명 규칙을 따르고, 설정된 formatter와 linter를
  사용합니다. 구체적인 규칙은 선택된 언어·도구 가이드를 참고합니다.
- **Intent-Revealing Names:** 축약어 대신 의도를 드러내는 명확한 이름을 사용합니다. (`d` -> `daysSinceCreation`)
- **Single Responsibility (SRP):** 하나의 함수나 클래스는 하나의 명확한 책임만 갖도록 합니다.
- **Control Flow:** 중첩을 줄이되 guard clause, expression, pattern matching 등 선택된
  언어가 의도를 가장 잘 드러내는 제어 흐름을 사용합니다.

### 3.2 타입 안정성 및 Null 안전성
- 언어별 타입 시스템(TypeScript, Java/Kotlin, Go 등)을 적극 활용하여 컴파일 타임 안전성을 확보합니다.
- 외부 입력은 런타임 경계(API 요청, DB 조회, 외부 서비스 응답)에서 검증합니다.
- 부재와 실패는 언어가 제공하는 nullable type, 다중 반환, error value, `Optional`,
  discriminated union 등 해당 언어에서 관용적인 모델로 표현합니다. 한 언어의 방식을
  다른 언어에 강제로 모사하지 않습니다.

### 3.3 아키텍처 및 의존성
- 입력 경계, use case, domain, 외부 시스템 adapter의 책임과 의존 방향을 분리하되,
  구체적인 계층과 추상화 형태는 선택된 언어와 프레임워크의 관용구를 따릅니다.
- DDD는 directory 이름이나 계층 template이 아니라 복잡한 업무 규칙, bounded context와
  ubiquitous language를 모델링하는 접근입니다. aggregate, domain service와 event는 실제
  불변식과 협력 규칙이 있을 때 도입하고 단순 CRUD에 형태만 복제하지 않습니다.
- 선택된 architecture profile은 기본 방향입니다. 저장소의 기존 구조나 배포·소유권 경계가
  더 강한 근거를 가지면 의존 방향을 보존하는 범위에서 프로젝트 지침으로 재정의합니다.
- OCP(Open-Closed Principle)를 지향하고, 매직 넘버나 하드코딩된 값은 상수 또는 설정 파일로 분리합니다.
- 실패를 삼키지 않고 언어별 error/exception/result 관용구로 원인과 의미를 보존합니다.

### 3.4 성능 및 보안
- Stream, Connection 등 외부 리소스의 수명 주기와 누수 방지를 확인합니다.
- 외부 입력값의 유효성 검증(Validation) 누락 여부를 확인합니다.
- 토큰, 비밀번호, 내부 URL, 고객 개인정보는 설정, 코드, 로그, 테스트 픽스처에 포함하지 않습니다.

## 4. 검증과 안전

### 4.1 로컬 검증 및 보고
- 저장소의 테스트 프레임워크와 테스트 파일 명명 규칙을 따르고, 설정에 명시된 커버리지
  기준을 적용합니다. 확인하지 않은 커버리지 목표를 임의로 추가하지 않습니다.
- 프로젝트가 정의한 전체 로컬 검증 진입점(테스트, 린트, 빌드)을 실행합니다.
- 실패한 검증을 우회하거나 일부 성공을 전체 성공으로 보고하지 않습니다.
- 실행한 명령, 통과 범위, 실행하지 못한 검증을 구분해 기록합니다.
- 커밋 전에는 변경 파일과 생성물을 확인해 의도치 않은 파일이 포함되지 않았는지 점검합니다.

### 4.2 안전 규칙
- 파일 삭제, 이력 변경(`reset --hard`, `rebase`), 원격 `push`, 운영 환경 변경은 명시적으로 승인된 범위에서만 수행합니다.
- 자동화가 관리하는 파일과 프로젝트가 직접 관리하는 파일의 소유권을 명확히 합니다.

## 5. 커밋 및 협업 규칙
- Conventional Commits 컨벤션(`feat:`, `fix:`, `refactor:`, `chore:` 등)을 준수합니다.
- 하나의 PR과 커밋은 가급적 하나의 논리적 변경만 포함하도록 분리합니다.
